# Consumer 再平衡

定义: 将一个Topic下的多个队列(或称之为分区)，在同一个消费者组(consumer group)下的多个消费者实例(consumer instance)
之间进行重新分配

弊端：
消费暂停: 队列在消费端重新分配期间，消息无法被消费，导致消费暂停
重复消费: 队列分配给新的消费者实例后，新的消费者实力会从旧的消费者实例的消费进度 ofset 处开始消费, 但是这个 offset
是异步提交的, 不一定是最新的, 可能会导致重复消费
消费突刺: 因为 Reblance 可能导致重复消费或 Reblance 暂停时间过长, 可以导致 reblance 完成后, 瞬间需要消费的消息变多

## Broker 端

协调者

订阅Topic的队列数量变化 (队列扩容/缩容)
消费者组信息变化 (消费者实例上线/下线, 消费者扩容/缩容)

```java
public class BrokerController {
    // Topic 配置管理器
    private TopicConfigManager topicConfigManager;

    // 消费者管理类，维护消费者组的注册实例信息以及 topic 的订阅信息，并对消费者 id 变化进行监听
    private final ConsumerManager consumerManager;

    // 订阅分组关系管理器，维护消费者组的一些附加运维信息
    private final SubscriptionGroupManager subscriptionGroupManager;

    // 消费者偏移量管理器，维护 offset 进度信息
    private final ConsumerOffsetManager consumerOffsetManager;
}
```

队列消息: TopicConfigManager --> 定时同步到 NameServer, 消费者和生产者定时从 NameServer 拉取最新的 Topic (定时拉取,
发现变更, 进行更新)

消费者信息: ConsumerManager + SubscriptionGroupManager + ConsumerOffsetManager (Broker 通知所有 Consumer
NOTIFY_CONSUMER_IDS_CHANGED, Broker 的 ConsumerManager 维护了对应 Topic 监听的消费者实力)

注: Consumer 会定时向 Broker 发送心跳 HEART_BEAT, 进行数据更新, UNREGISTER_CLIENT 进行下线， Broker 同时会进行心跳检查, 移除

## Consumer 端

Consumer 消费消息 2 种方式 Push 和 Pull, 

### Push 模式

1. 启动时, Consumer 会向 Broker 发送心跳, 注册自己, 并拉取 Topic 信息, 触发 Rebalance (MQClientInstance.rebalanceImmediately)
2. 收到 Broker 的 NOTIFY_CONSUMER_IDS_CHANGED 通知, 触发 Rebalance
3. 定时拉取 Topic 信息, 变更, 触发 Rebalance


### RocketMQ rebalance 存在的一个问题

如果一个消费者组订阅多个Topic，可能会出现分配不均，部分消费者处于空闲状态。

RocketMQ 是按照 Topic 维度进行队列分配的，假设有两个 TopicA，TopicB 各有 2 个队列, 现在有 4 个消费者实例。可能会出现下面的分配方式
> 1. 先分配 TopicA 的 2 个队列, 消费者实例 1 和 2 分别分配到一个队列, 实例 3 和 4 没有分配到任何队列
> 2. 再分配 TopicB 的 2 个队列, 消费者实例 1 和 2 分别分配到一个队列, 实例 3 和 4 仍然没有分配到任何队列

那么就存在 消费者实例 C1 和 C2 各处理 2 个队列的消息, 而 C3 和 C4 处于空闲状态


注: kafka 则是将所有Topic下的所有队列合并在一起, 然后进行分配, 这样相对平衡一些。


Reblance 逻辑

```java
// isOrder 表示是否是顺序消费
private void rebalanceByTopic(final String topic, final boolean isOrder) {
    switch (messageModel) {
        case BROADCASTING: {
            // 广播模式

            // 广播模式，不需要重新分配队列，直接使用当前 Topic 下的所有消息队列
            Set<MessageQueue> mqSet = this.topicSubscribeInfoTable.get(topic);
            if (mqSet != null) {
                // 根据新分配的结果, 尝试更新 ConcurrentMap<MessageQueue, ProcessQueue> processQueueTable, 并返回是否变更
                boolean changed = this.updateProcessQueueTableInRebalance(topic, mqSet, isOrder);
                if (changed) {
                    this.messageQueueChanged(topic, mqSet, mqSet);
                }
            }
            break;
        }
        case CLUSTERING: {
            // 集群模式
            // 获取当前 Topic 在 NameServer 下所有的消息队列
            Set<MessageQueue> mqSet = this.topicSubscribeInfoTable.get(topic);
            // 获取当前消费者组下所有的消费者 ID
            // 向 Broker 发送 GET_CONSUMER_LIST_BY_GROUP
            List<String> cidAll = this.mQClientFactory.findConsumerIdList(topic, consumerGroup);

             if (mqSet != null && cidAll != null) {
                List<MessageQueue> mqAll = new ArrayList<MessageQueue>();
                mqAll.addAll(mqSet);
                // 对 队列和消费者 ID 进行排序, 保证所有的消费客户端都一致
                Collections.sort(mqAll);
                Collections.sort(cidAll);

                AllocateMessageQueueStrategy strategy = this.allocateMessageQueueStrategy;

                List<MessageQueue> allocateResult = null;
                try {
                    // 根据分配策略, 为当前的消费端分配消息队列
                    // this.mQClientFactory.getClientId() 获取本机器的消费者 ID, 在启动时声明好的， 默认为 机器的IP@配置的实例名称
                    allocateResult = strategy.allocate(
                            this.consumerGroup,
                            this.mQClientFactory.getClientId(),
                            mqAll,
                            cidAll);
                } catch (Throwable e) {
                    log.error("AllocateMessageQueueStrategy.allocate Exception. allocateMessageQueueStrategyName={}", strategy.getName(), e);
                    return;
                }

                Set<MessageQueue> allocateResultSet = new HashSet<MessageQueue>();
                if (allocateResult != null) {
                    allocateResultSet.addAll(allocateResult);
                }

                
                // 根据新分配的结果, 尝试更新 ConcurrentMap<MessageQueue, ProcessQueue> processQueueTable, 并返回是否变更
                // <MQ队列, MQ队列的处理队列> 判断这个 Map 是否需要变更 (ProcessQueue 存放了拉取并缓存的消息等)
                boolean changed = this.updateProcessQueueTableInRebalance(topic, allocateResultSet, isOrder);
                if (changed) {
                    // 有变更, 进行队列变更, 主要是把最新的订阅信息 以 心跳的方式发送给所有 Broker 
                    this.messageQueueChanged(topic, mqSet, allocateResultSet);
                }
            }
            break;
        }
        default:
            break;
}
```

消费者各自给自己分配队列, 如何解决脑裂问题
> 1. 对 Topic 队列，以及消费者各自进行排序
> 2. 使用相同的分配策略

新增的队列: 先计算从哪个位置开始消费，接着从这个位置开始拉取消息进行消费
删除的队列: 上报当前的 offset 给 Broker, 移除这个队列的 offset 的持久化
org.apache.rocketmq.client.impl.consumer.RebalancePushImpl#removeUnnecessaryMessageQueue


MQClientInstance 中有个属性 RebalanceService rebalanceService (ServiceThread) 用于处理消费者的再平衡, 默认 20s
自己唤醒一次 (可以通过 rocketmq.client.rebalance.waitInterval 配置)

最终调用到 org.apache.rocketmq.client.impl.consumer.RebalanceImpl.doRebalance 方法
